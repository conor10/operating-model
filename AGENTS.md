## Required First Steps

Before making current-state claims or edits:

1. Read `README.md`.
2. Read `STATUS.md` if present.
3. Check git status.
4. Inspect only the files needed for the task.
5. State any assumptions that affect the implementation or review.

## Modes

Respect the user's requested mode:

- **Advisory**: answer only; do not edit files.
- **Plan**: produce a plan; do not edit files.
- **Implement**: edit files within scope and verify.
- **Review**: do not edit files; findings first.

If the mode is unclear, prefer advisory/plan for risky or ambiguous work.

## Working Rules

- Keep changes small and reviewable.
- Prefer existing project patterns over new abstractions.
- Do not overwrite unrelated user changes.
- Do not run destructive commands unless explicitly requested.
- Do not commit secrets, credentials, tokens, or private data.
- Use structured parsers/APIs instead of brittle string manipulation when practical.
- Update docs only when behavior, process, or public usage changes.
- Gate commits on real exit codes: never trust `command | tail`-style pipelines
  for pass/fail (the pipe's status wins); check the command's own status before
  committing.
- Anything a model sees is versioned configuration — prompts, schemas, and the
  mechanism by which they are delivered. None of it is an unpinned
  implementation choice.
- Evolve file formats additively with tolerant readers; parsers fail closed on
  malformed input; no partial artifacts on error.
- Prefer deterministic, byte-reproducible artifacts. Derived outputs stay out
  of version control; the inputs and evidence that regenerate them stay in.
- Versioned/published artifacts are immutable: a change is a new version, never
  an edit in place.
- History is never rewritten. Records of what happened stay verbatim, even
  after renames or reversals.

## Quality Gates

Before claiming work is done, run the relevant checks:

- tests for behavior changes
- typecheck for typed projects
- lint/format when configured
- build for deployable applications
- runtime smoke tests for runtime-sensitive changes

Extra gates:

- **Database/schema changes**: verify migrations and affected runtime paths.
- **Auth/security/privacy changes**: perform adversarial review.
- **External integrations**: document API assumptions and failure modes.
- **Deploy changes**: verify the deployed entrypoint, not just local build.
- **Requirement-ID boundaries**: implementer prompts define stable requirement
  IDs (`XX-nn`); tests reference them with `# verifies: XX-nn` markers;
  regenerate `docs/TRACEABILITY.md` and keep its staleness guard green whenever
  a boundary adds or changes a marker.

## State And Decision Docs

- `STATUS.md` tracks current project state and next step.
- `DECISIONS.md` records non-trivial decisions, alternatives, rationale, and consequences.
- `ROADMAP.md`, if present, tracks product sequencing, not tactical progress.
- `TASKS.md`, if present, is the agent-readable task register: per-person
  assignments with status. Agents acting for an assignee read the whole repo
  but submit deliverables via the channel named in the task or a branch/PR —
  never direct pushes to the main branch. (Optional — useful once more than
  one person delegates to agents.)
- `SME-REVIEW.md`, if present, registers open domain-expert questions.
  Regardless of whether the file exists yet: any agent that surfaces a domain
  question it cannot resolve must record it (question, source link, interim
  default) rather than deciding silently — **creating this register from the
  template if the project doesn't have one** — never burying it in a run
  record.
- `docs/TRACEABILITY.md`, once the project has tests, is generated by
  `tools/traceability.py` from requirement IDs and `# verifies:` markers —
  never edited by hand.
- `agent-runs/` stores meaningful prompt/run/review records.

Update state docs only when the task changes project state or process. Do not update them for casual Q&A.

## Review Mode

When asked for review:

1. Findings first.
2. Order by severity.
3. Include file/line references when possible.
4. Explain impact and a concrete fix.
5. Include missing tests or verification gaps.
6. End with `Ship`, `Ship with known issues`, or `No ship`.

## Multi-Agent Rules

- One workspace owns edits.
- Planner and judge/reviewer roles are read-only by default.
- Use commits, branches, worktrees, or saved diffs as handoff boundaries.
- Do not let multiple agents edit the same files without an explicit integrator.
- Implementers may deviate from a dispatch prompt only by declaring the
  deviation and its reason in their summary; the judge adjudicates it
  explicitly (a plausible deviation is often the prompt's error, not the
  implementer's).
- Human remains final authority for merge/deploy decisions.

## Security And Privacy

- Never expose secrets in prompts, logs, diffs, or screenshots.
- Redact sensitive data in agent-run records.
- Treat production/customer data as out of scope unless explicitly approved.
- Call out compliance or privacy risk before proceeding.
